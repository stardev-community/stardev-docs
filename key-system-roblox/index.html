Key system Roblox: cara kerjanya dan cara punya sendiri

Key system adalah pintu masuk sebelum script berjalan: pengguna menempel key, server memeriksa key itu masih aktif dan dipakai di perangkat yang benar, baru scriptnya dieksekusi. Di balik layar hanya ada tiga hal — key, HWID, dan masa aktif.

Alur satu kali verifikasi

  1. Script memanggil endpoint verifikasi dengan key, hwid, dan id produk.
  2. Server mencari key di database, memeriksa status, tanggal kedaluwarsa, dan jumlah perangkat terdaftar.
  3. Kalau cocok, HWID dicatat (atau dicocokkan dengan yang lama) dan server mengembalikan token sesi.
  4. Script menyimpan token di memori, bukan di file, lalu lanjut berjalan.

Kegagalan yang paling sering terjadi bukan "key salah", tapi HWID berubah setelah update sistem atau ganti perangkat, dan key yang sama dipakai berpindah-pindah.

Contoh panggilan dari Luau

local HttpService = game:GetService("HttpService")

local function hwid()
    -- gabungkan beberapa nilai perangkat; jangan pakai yang berubah tiap sesi
    return HttpService:GenerateGUID(false)
end

local body = HttpService:JSONEncode({
    key  = "LULU-XXXX-XXXX",
    hwid = hwid(),
    app  = "my-script"
})

local ok, res = pcall(function()
    return HttpService:RequestAsync({
        Url    = "https://your-app.vercel.app/api/verify",
        Method = "POST",
        Headers = { ["Content-Type"] = "application/json" },
        Body   = body
    })
end)

if not ok or not res.Success then
    return warn("Verifikasi gagal, script berhenti.")
end

local data = HttpService:JSONDecode(res.Body)
if not data.valid then
    return warn(data.message or "Key tidak valid.")
end
-- lanjut inisialisasi script

Di Roblox, permintaan HTTP hanya bisa ke domain yang diizinkan dan dari server script. Jangan taruh secret admin di client.

Kesalahan yang bikin key system bocor

  • Menaruh logika verifikasi di client saja — bisa dilewati dengan mengubah script.
  • HWID dari nilai acak tiap sesi, sehingga key selalu "salah perangkat".
  • Tidak ada rate limit, jadi key bisa ditebak berulang.
  • Secret admin ikut terkirim ke client atau tersimpan di repo publik.
  • Tidak ada pencatatan percobaan gagal, sehingga penyalahgunaan tidak terlihat.
