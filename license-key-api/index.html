Designing a license key API that does not need rewrites

Most licensing rewrites happen because the API leaked implementation details too early. Four endpoints and three rules avoid that.

The four endpoints

EndpointPurposeAuth
POST /api/verifyValidate key + HWID, return expiryApp secret
/api/adminCreate, edit, delete keysAdmin secret
/api/hwidBlock or unblock device idsAdmin secret
/api/securityRead failure eventsAdmin secret

Three rules

  1. Verify is read-mostly. It may register a HWID slot, but it must not silently extend expiry.
  2. Errors are data, not HTTP codes. Return 200 with valid:false and a machine-readable code; reserve 4xx/5xx for transport and auth.
  3. Creation is idempotent. Accept a client-generated request id so a retried POST does not mint duplicate keys.

Idempotent creation

POST /api/admin
{"op":"create","count":10,"days":30,"requestId":"7f3c..."}
→ {"created":["K1","K2"],"requestId":"7f3c..."}
→ retry with same requestId returns the same list

Rate limits that do not punish buyers

Limit per HWID and per key, not per IP: mobile carriers share IPs, and shared NAT would lock out legitimate users. Five attempts per hour is generous for a real client.
