Running your own key server

Self-hosting removes the vendor from the path between your product and its keys. It also removes the person who used to handle backups at 2am.

The minimum shape

PieceJob
Verify endpointKey + HWID check, expiry, slot registration
Key storeKey, owner label, expiry, plan, slot list
Admin surfaceCreate, revoke, block, inspect
Event logFailed attempts with reason codes

Redis layout that stays readable

key:<KEY>        hash  {status, expireAt, maxHwid, plan}
key:<KEY>:hwids set   [hwid, ...]
hwid:blocked     set   [hwid, ...]
events           list  (capped, newest first)

Keep one hash per key and one set per key's devices. Avoid a single JSON blob for everything — you will rewrite it the first time two requests race.

Race conditions

Two devices activating at the same moment can both see "1 of 2 slots free". Use an atomic check-and-add (Lua script or WATCH/MULTI) so the slot count cannot exceed the limit.

Backups and rotation

Export keys and device lists daily. Rotate the admin secret and the signing key pair on a schedule, and keep the old public key available until shipped clients have updated.

What you get for the effort

No plan ceiling, no queue for resets, and key data you can audit. The cost is operational: uptime, backups, and the occasional race condition.
